### C-001  C-004 "Block this person" is cosmetic — nothing in the app or the database ever reads user_blocks
- severity: blocker
- area: chat
- confidence: confirmed-in-code
- evidence: /Volumes/mindfulssd/dev/OVercomersapp2026/lib/chatService.ts:607-619 upserts into user_blocks. A repo-wide `grep -rn 'user_blocks' app lib components` returns exactly one hit — that writer. No reader exists. Confirmed on the live database too: the SELECT policy on chat_messages is "members read messages", whose qual is `is_chat_moderator() OR (deleted_at IS NULL AND (is_flagged = false OR user_id = auth.uid()) AND EXISTS (SELECT 1 FROM chat_members cm WHERE cm.channel_id = chat_messages.channel_id AND cm.user_id = auth.uid()))`. It never mentions user_blocks. The only visible effect of the button is app/chat-room.tsx:381, `setMessages((current) => current.filter((item) => item.userId !== message.userId))`, which is in-memory only.
- cause: The block writes a row and then filters the local array. Nothing re-applies that filter on the next fetch, and the server does not apply it either. So the blocked person's messages are gone until the room is closed and reopened, or the app is restarted, and then they are back. A reviewer who blocks a user and pulls to refresh sees the block fail, which is the exact check Apple 1.2 asks for.
- fix: In lib/chatService.ts, add `listBlockedUserIds()` that selects blocked_user_id from user_blocks for the current user, and have loadChatMessages apply `.not('user_id', 'in', '(' + ids.join(',') + ')')` when the set is non-empty (and skip the clause entirely when it is empty, so an empty set does not produce a malformed filter). Cache the set per session and invalidate it inside blockChatUser. Apply the same set to the story ring for C-003. Do NOT push this into the RLS policy in this release.
- risk: DO-NOT-BREAK item 6 is the live wire here: chat history reads only after self-join of public rooms via joinChatRoom, and a `profiles(...)` embed on chat_messages has no FK and silently 400s. A client-side .not() filter on user_id touches neither. Changing the "members read messages" RLS policy instead would put items 5 and 6 at risk in one edit and is the reason to keep this in the client.

### C-002  The content filter is defeated by editing: both triggers are BEFORE INSERT only and members can PATCH is_flagged and status to false
**STATUS: FIXED 2026-09-19 before Phase 2.**
- severity: blocker
- area: chat
- confidence: confirmed-in-code
- evidence: pg_get_triggerdef shows CREATE TRIGGER chat_message_auto_review BEFORE INSERT ON public.chat_messages and CREATE TRIGGER app_story_auto_review BEFORE INSERT ON public.app_stories — no UPDATE trigger on either table. The policy "members delete own messages" is cmd=UPDATE, USING (user_id = auth.uid()), WITH CHECK (user_id = auth.uid()) with no column restriction, and chat_messages.body and chat_messages.is_flagged are ordinary columns (confirmed via pg_attribute). The policy "authors update their own story" is cmd=UPDATE, USING and WITH CHECK both (created_by = auth.uid()), and app_stories.status is an ordinary column with default 'published'. authenticated holds table-wide UPDATE on both tables.
- cause: The filter only ever runs on the first write. A member posts an innocuous message, then issues PATCH /rest/v1/chat_messages?id=eq.<their own id> with {"body":"<abuse>","is_flagged":false}; the policy passes because user_id is still theirs, no trigger fires, and "members read messages" then shows the edited body to the whole room because is_flagged is false and deleted_at is null. The story path is worse: if app_story_auto_review does hold a story (it sets new.status := 'draft' and new.published_at := null), the author can simply PATCH status back to 'published', so the hold is reversible by the very person it was applied to. This defeats DO-NOT-BREAK item 18 — the filter is nominally in the database, but nothing enforces it after insert.
- fix: Two edits, both in SQL. (1) Add BEFORE UPDATE triggers that re-run content_needs_review whenever body (chat_messages) or title/body (app_stories) changes — reuse the existing chat_message_auto_review and app_story_auto_review functions, adding WHEN (OLD.body IS DISTINCT FROM NEW.body). (2) Narrow the member UPDATE policies so the author cannot change the moderation columns: replace the WITH CHECK on "members delete own messages" with (user_id = auth.uid() AND is_flagged IS NOT DISTINCT FROM (SELECT is_flagged FROM chat_messages WHERE id = chat_messages.id)) or, more simply and more robustly, move the member's soft-delete to a SECURITY DEFINER RPC that only ever sets deleted_at, and drop the broad UPDATE policy.
- risk: DO-NOT-BREAK item 19 — a member must keep being able to soft-delete their own chat message. Any narrowing of the UPDATE policy has to leave deleted_at writable by the author or that regresses. DO-NOT-BREAK item 5 also requires that moderators keep their own UPDATE path ("moderators moderate messages" USING is_chat_moderator()), which must not be touched.

### C-003  Any signed-in member can read, rewrite or delete every other member's profile through the chat_profiles view
**STATUS: FIXED 2026-09-19 before Phase 2.**
- severity: blocker
- area: security
- confidence: confirmed-in-code
- evidence: pg_class.reloptions on public.chat_profiles = {security_invoker=false}; relacl grants authenticated=arwdDxtm/postgres; pg_relation_is_updatable('public.chat_profiles'::regclass, true) returns 28 = UPDATE(4)|INSERT(8)|DELETE(16); pg_column_is_updatable for display_name and avatar_url both return true; view owner = postgres and profiles.relforcerowsecurity = false. Supabase security advisor lint 0010_security_definer_view, level ERROR, names this exact view. All 7 profile rows are returned by SELECT * FROM chat_profiles.
- cause: With security_invoker=false the view executes as its owner, postgres. Postgres owns public.profiles and public.user_roles, and neither has FORCE ROW LEVEL SECURITY, so a table owner bypasses RLS entirely. The profiles policies — "users read own profile" USING ((id = auth.uid()) OR is_staff_or_above()) and "users update own profile" USING (id = auth.uid()) — are therefore never evaluated for anyone querying through the view. The read side is deliberate (lib/chatService.ts:624 comments that chat_profiles is "names and pictures, which every signed-in person" can see), but the INSERT/UPDATE/DELETE grant is not: the view is auto-updatable on its simple columns, so a member can PATCH another member's display_name and avatar_url, and DELETE their profile row outright. profiles has no DELETE policy at all, which means this view is the only delete path in the schema and it is open to every member.
- fix: REVOKE INSERT, UPDATE, DELETE ON public.chat_profiles FROM authenticated; leaving SELECT intact. Do NOT 'fix' this by setting security_invoker=true — that is the obvious move and it is wrong here.
- risk: Setting security_invoker=true would break DO-NOT-BREAK item 6. chat_profiles is how every author name and avatar in chat is resolved — lib/chatService.ts:633, :683, :789, app/person.tsx:60 and supabase/migrations/20260918090000_chat_member_roster.sql:9 all read it — and under invoker semantics profiles RLS would collapse each member's view to their own row, so every message in the Global Prayer Room would render as "OGN Member". Revoking only the write privileges preserves the roster exactly.

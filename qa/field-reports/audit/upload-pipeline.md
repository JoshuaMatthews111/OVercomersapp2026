## S3 — Story publish uploads the full-resolution file through a 4-copy JS/base64 path with no progress
**severity** blocker · **confidence** confirmed-in-code
**files** lib/uploadBody.ts:8, lib/uploadBody.ts:10, lib/uploadService.ts:34, lib/uploadService.ts:36, app/admin.tsx:203, app/admin.tsx:208, package.json:31
**root cause** No downscaling exists anywhere in the app. app/admin.tsx:203 picks with `quality: 0.86`, which re-encodes JPEG but never changes pixel dimensions, so a 12 MP photo stays 12 MP (3-5 MB). expo-image-manipulator is NOT in package.json and NOT in node_modules. lib/uploadBody.ts:8-13 then reads the ENTIRE file into one JS ArrayBuffer: `const file = new File(uri); ... const body = await file.arrayBuffer();` — and expo-file-system/src/File.ts:186-189 implements that as `(await this.bytes()).buffer`, i.e. the whole file materialised in JS. lib/uploadService.ts:36-41 hands that ArrayBuffer to storage-js, which (dist/umd/supabase.js `uploadOrUpdate`) only special-cases Blob and FormData and otherwise passes the body straight to fetch. RN's fetch is whatwg-fetch over XHR (react-native/Libraries/Network/fetch.js), which at fetch.umd.js:261 does `this._bodyArrayBuffer = bufferClone(body)` (copy 2), and xhr.send reaches RCTNetworking.ios.js:42 `convertRequestBody(data)` -> convertRequestBody.js:38-41 `return {base64: binaryToBase64(body)}` -> a pure-JS `base64.fromByteArray` (copy 3, 1.33x, as a JS string), which native then decodes back to bytes (copy 4). So a 4 MB photo costs ~18 MB of transient allocation plus a JS base64 pass, on top of pushing an unreduced 4 MB over a phone uplink. Publishing is also serial: getUser (network, auth-js GoTrueClient.js:2590 `GET ${url}/user`) -> file read -> upload -> recordUploadedFile (uploadAnalysis.ts:51 another getUser + insert) -> createAdminStory (contentService.ts:301 a third getUser + insert).
**fix plan** 1) Add expo-image-manipulator and introduce `lib/prepareImage.ts` that resizes any picked image to a max 1600 px long edge at quality 0.75 (512 px for avatars) and returns a new file URI; call it in app/admin.tsx StoryForm.pickMedia (line 203-208), MediaForm.pickCover (278-283), EventForm.pickFlyer (349-354), app/index.tsx pickSignupAvatar (146-152), app/(tabs)/profile.tsx (166-176) and components/ChatAttachments.tsx pick() (37-45). 2) Replace the ArrayBuffer transport in lib/uploadBody.ts / lib/uploadService.ts with expo-file-system's `UploadTask` (build/NetworkTasks.d.ts, already installed at 57.0.7) using `UploadType.BINARY_CONTENT` against a URL from `supabase.storage.from(bucket).createSignedUploadUrl(path)`, wiring `onProgress` up to the caller. 3) In lib/uploadService.ts take the user id from a single cached `getSession()` instead of three `getUser()` calls, and pass it into `recordUploadedFile` so uploadAnalysis.ts:51 stops re-fetching it. 4) Stop awaiting `recordUploadedFile` (lib/uploadService.ts:46) before returning; fire it after the URL is resolved. 5) Surface a percent + cancel UI on the story form instead of the `saving ? 'Working...'` label at app/admin.tsx:244.
**risk** expo-image-manipulator is a new native module: DO-NOT-BREAK #22 means this must ship as a new EAS build, not an OTA update. Changing the storage transport must not make the `chat-attachments` bucket public or bypass signed links (DO-NOT-BREAK #20) — the signed-upload-URL route keeps the bucket private. Resizing must not touch the approved crest/seal or Give imagery assets (DO-NOT-BREAK #11); it applies only to user-picked media. Story expiry/publish semantics (DO-NOT-BREAK #15, #16) are untouched by this change.

## C5 — 50 MB video cap is hard-coded in two places, and even raising it fails on memory and on a 120 s wall-clock deadline
**severity** blocker · **confidence** confirmed-in-code
**files** lib/uploadBody.ts:6, lib/uploadBody.ts:9, lib/uploadBody.ts:12, components/ChatAttachments.tsx:63, lib/supabase.ts:15, lib/requestTimeout.ts:8
**root cause** Three independent walls stop a normal phone video.
(a) The cap: lib/uploadBody.ts:6 `export async function readUploadBody(uri: string, maxBytes = 50 * 1024 * 1024)` with throws at lines 9, 12 and 19, and a second client-side copy at components/ChatAttachments.tsx:63 `if (file.size && file.size > 50 * 1024 * 1024) return Alert.alert('File too large', ...)`. No caller ever overrides `maxBytes`.
(b) Memory: even if the cap were raised, the ArrayBuffer path from S3 means a 50 MB video becomes a 50 MB ArrayBuffer + a 50 MB bufferClone (whatwg-fetch dist/fetch.umd.js:261) + a ~67 MB base64 JS string (convertRequestBody.js:41 -> binaryToBase64 -> base64-js `fromByteArray`) + a 50 MB native Data — roughly 220 MB of transient allocation for one send.
(c) Time: lib/supabase.ts:15 gives storage uploads 120000 ms, and lib/requestTimeout.ts:8 `const timer = setTimeout(cancel, timeoutMs)` starts that clock when the request begins and never resets it. It is a wall-clock deadline, not an idle timeout. 50 MB over a typical 1-3 Mbps phone uplink is 130-400 s, so a large-but-legal file is guaranteed to abort partway with a bare 'Aborted'/'Network request failed'.
There is no compressor installed to shrink the file: no expo-image-manipulator, no expo-av, no react-native-compressor, no ffmpeg. `videoQuality: ImagePicker.UIImagePickerControllerQualityType.Medium` at ChatAttachments.tsx:43 is iOS-only (expo-image-picker/build/ImagePicker.types.d.ts:443-446 `@platform ios`) and is absent from the camera branch at ChatAttachments.tsx:37.
**fix plan** Fix in this order, because raising the cap alone makes things worse. 1) Move to the streaming transport first: expo-file-system `UploadTask` (UploadType.BINARY_CONTENT) against `createSignedUploadUrl` — it streams from the file URI so (b) disappears entirely and progress becomes available. 2) Change lib/requestTimeout.ts to an idle/stall timeout: reset the timer on each progress tick rather than a single `setTimeout` at line 8, or drop the deadline for uploads and rely on the UploadTask's own AbortSignal plus a user-visible Cancel. 3) Then raise `maxBytes` in lib/uploadBody.ts:6 and the mirror check in components/ChatAttachments.tsx:63 to a matching, single shared constant — and confirm the Supabase bucket's own `file_size_limit` on `chat-attachments` is at least as large, since a server-side cap will still 413. 4) Set `videoExportPreset`/`videoQuality` on the camera branch too (ChatAttachments.tsx:37), and add `react-native-compressor` if a true 1-minute 4K video must send.
**risk** New native modules mean a new EAS build, not an OTA (DO-NOT-BREAK #22). Raising the client cap without also raising the bucket limit converts a clear 'File too large' message into an opaque 413. Keep `chat-attachments` private and signed-link-only (DO-NOT-BREAK #20). Changing lib/requestTimeout.ts affects EVERY supabase request (lib/supabase.ts:15 is the only consumer) — the 15 s default for normal queries must stay, or slow screens start hanging instead of erroring.

## NEW-1 — Three raw fetch() calls have no timeout; requestTimeout.ts is wired at exactly one place
**severity** high · **confidence** confirmed-in-code
**files** lib/bibleProvider.ts:163, lib/bibleProvider.ts:206, lib/evangelismService.ts:71, lib/uploadBody.ts:15, lib/supabase.ts:15

The signed-upload-URL route must preserve the existing object paths (`<room>/<user>/...` for chat, `stories/...`, `media-thumbnails/...`) so storage policies keep matching, and `chat-attachments` must stay private with signed-link reads (DO-NOT-BREAK #20). ## NEW-3 — fetchWithTimeout is a wall-clock deadline, not a stall timeout, so long legitimate uploads are aborted
**severity** medium · **confidence** confirmed-in-code
**files** lib/requestTimeout.ts:1, lib/requestTimeout.ts:8, lib/supabase.ts:15
**root cause** lib/requestTimeout.ts:1 documents itself as 'Bound a stalled network request while preserving a caller's cancellation', but line 8 is a single `const timer = setTimeout(cancel, timeoutMs);` armed once before the request starts and never re-armed. Nothing observes bytes in flight, so a request that is transferring perfectly well at a steady rate is aborted the moment it crosses the budget. Combined with lib/supabase.ts:15, which grants storage uploads 120000 ms, any upload that legitimately needs more than two minutes — which a 20-50 MB file does on a normal phone uplink — is killed mid-transfer and surfaces to the user as a generic abort. The user-visible symptom is exactly C5's 'a one-minute video failed'. A secondary effect of the same line: the predicate `String(input).includes('/storage/v1/object/') && init?.body` also matches `POST /storage/v1/object/sign/...` (createSignedUrl / createSignedUrls), so those small metadata calls silently get the 120 s budget instead of 15 s and will hang for two minutes if storage is unhealthy.
**fix plan** Rewrite lib/requestTimeout.ts to reset its timer on activity rather than firing once: with the UploadTask transport from S3 that is trivial (re-arm on each `onProgress` tick); for the remaining fetch path, either drop the deadline for upload requests entirely and rely on a user-visible Cancel, or raise it well past any realistic transfer. Separately, tighten the predicate at lib/supabase.ts:15 so it matches only actual object writes (e.g. exclude paths containing '/object/sign/'), keeping the 15 s budget on signing calls.
**risk** This function is the timeout for EVERY supabase request in the app. Removing or lengthening the general 15 s budget would turn today's clean 'try again' errors into indefinite spinners on Chat, Media and Home. Change the upload branch only; leave the 15 s default untouched.

## A1 — Every admin upload reads the whole file into JS memory and React Native base64-encodes it on the JS thread before any byte is sent — this is the 5-10 minutes
**severity** blocker · **confidence** confirmed-in-code
**files** lib/uploadBody.ts:10, lib/uploadService.ts:34, lib/uploadService.ts:36, lib/supabase.ts:15, node_modules/react-native/Libraries/Network/convertRequestBody.js:38
**root cause** lib/uploadBody.ts:6-13 is the native path for every admin upload: `const file = new File(uri); ... const body = await file.arrayBuffer(); ... return { body, size: body.byteLength }` with `maxBytes = 50 * 1024 * 1024`. So the complete file — up to 50 MB — lands in the JavaScript heap as one ArrayBuffer. lib/uploadService.ts:34 then does `const upload = await readUploadBody(input.asset.uri)` and lib/uploadService.ts:36-41 hands that buffer straight to `supabase.storage.from(bucketId).upload(objectPath, upload.body, {...})`. supabase-js posts it through the app's own fetch (lib/supabase.ts:15), which is React Native's fetch. I read what React Native does with an ArrayBuffer body: node_modules/react-native/Libraries/Network/convertRequestBody.js:38-41 reads `if (body instanceof ArrayBuffer || ArrayBuffer.isView(body)) { return {base64: binaryToBase64(body)}; }`, and node_modules/react-native/Libraries/Utilities/binaryToBase64.js calls `base64.fromByteArray(data)` from the base64-js package — a synchronous pure-JavaScript loop. So for a 40 MB video the sequence is: allocate 40 MB in the Hermes heap, synchronously build a ~53.3 MB JavaScript string one character at a time on the JS thread, marshal that 53 MB string across the bridge, base64-decode it natively, and only then start the HTTP PUT. The encode alone is minutes of blocked JS on a phone, the payload on the wire is 33% larger than the file, and the PUT is a single non-resumable request with no progress events. This is one mechanism producing all three symptoms the owner reported: extreme slowness, a UI that stops responding, and no way to tell whether it is still working. A second consequence: lib/supabase.ts:15 sets the storage timeout with `setTimeout(cancel, 120000)` BEFORE calling fetch (lib/requestTimeout.ts:8 then :10), but the base64 encode happens synchronously inside that fetch call, so the timer cannot fire while the JS thread is blocked and the remaining network budget is whatever is left of the 120 s. Near the 50 MB cap the abort can land mid-upload, and the user is told 'Upload failed' after minutes of waiting.
**fix plan** Replace the buffer-and-base64 path with the native streaming upload that expo-file-system 57 already ships — no new dependency and no new native module, so this stays OTA-compatible with the current build. I verified the API exists in node_modules/expo-file-system/build/File.d.ts:121-145 and NetworkTasks.d.ts/NetworkTasks.types.d.ts: `file.createUploadTask(url, { uploadType: UploadType.BINARY_CONTENT, headers, onProgress: ({ bytesSent, totalBytes }) => ..., signal })` then `await task.uploadAsync()`. Rewrite `uploadPickedAsset` and `uploadDocumentAsset` in lib/uploadService.ts to POST directly to the Supabase Storage REST endpoint `${SUPABASE_URL}/storage/v1/object/${bucketId}/${objectPath}` with headers `{ Authorization: 'Bearer ' + session.access_token, apikey: SUPABASE_ANON_KEY, 'Content-Type': mimeType, 'x-upsert': 'true' }`, taking the token from `supabase.auth.getSession()` (local, no network) rather than `getUser()`. Add an `onProgress` callback to the input signature and thread it up into StoryForm/MediaForm/EventForm. Delete the native branch of lib/uploadBody.ts:7-13 once nothing calls it; keep the web Blob branch at :15-20 (browsers stream Blobs correctly). Raise or remove the 50 MB cap at lib/uploadBody.ts:6 only after the streaming path lands — with streaming the cap is a policy choice, not a memory limit (this also unblocks C5). Verify by posting a 1-minute phone video from Admin and watching the progress percentage move.
**risk** Uploads are load-bearing for stories (DO-NOT-BREAK 8, 15), chat attachments (20) and profile photos (9). The private `chat-attachments` bucket must stay private (item 20) — if lib/uploadService.ts:107-119 `getReachableStorageUrl` is refactored alongside this, keep the signed-URL branch for every non-public bucket and keep the public set exactly `['app-assets','story-media','profile-avatars']`. Direct REST upload bypasses supabase-js, so storage RLS is enforced by the token you send — a mistake here could either break uploads or, worse, upload with the wrong identity; test with the fableqa member account as well as an admin. Item 22 means verify whether this needs a new EAS build: expo-file-system is already in the build, so it should not, but confirm before shipping as OTA only.

## A1 — No progress feedback exists in any admin post form — the Shell spinner is wired to a state the forms never set
**severity** blocker · **confidence** confirmed-in-code
**files** app/admin.tsx:557, app/admin.tsx:81, app/admin.tsx:200, app/admin.tsx:234, app/admin.tsx:244
**root cause** Admin has exactly one progress indicator: app/admin.tsx:557, `{busy ? <ActivityIndicator color={colors.gold} /> : <View style={{ width: 24 }} />}` in the Shell header. `busy` is set only inside `run()` (app/admin.tsx:80-91: `setBusy(true)` at :81, `setBusy(false)` at :89), and `run` is used only by the review, people and library action buttons. Every posting form keeps its own private state instead — StoryForm `const [saving, setSaving] = useState(false)` (app/admin.tsx:200), MediaForm (:258), EventForm (:346), NoticePage `sending` (:475) — and none of them is passed to Shell, because Shell receives `busy={busy}` from the screen-level state at app/admin.tsx:113. So during the single slowest operation in the app, the header spinner is structurally guaranteed not to appear. The only feedback the user gets is the button label flipping via `<Big label={saving ? 'Working...' : 'Post story'} disabled={saving} .../>` (app/admin.tsx:244) — static text, no spinner, no percentage, no byte count. Worse, the media pickers themselves are unguarded: app/admin.tsx:234 is `<Pressable ... onPress={pickMedia} style={[styles.dropzone, ...]}>` with no `disabled` prop, and pickMedia sets `saving` at :206 — so during a multi-minute upload the dropzone is still tappable and a second tap starts a concurrent upload of another file. The same holds for `pickFile` (:323), `pickCover` (:327) and `pickFlyer` (:381). Separately, the submit handlers are so short that the real wait is not in them: `post()` at app/admin.tsx:217-230 awaits `createAdminStory` (which itself does two sequential network round trips) and then Alert — only 2 awaits — because all the slow work already happened inside `pickMedia`, where the user's only clue is a button label in a different part of the form.
**fix plan** Lift progress into Shell. Change Shell's props in app/admin.tsx:547 from `busy?: boolean` to also accept `progress?: { label: string; fraction?: number }`, and render a determinate bar under the header when present. Give PostPage a shared progress state and pass a setter down to StoryForm/MediaForm/EventForm so the `onProgress` callback added in the A1 upload fix drives it — during a video upload the header should read e.g. 'Uploading video 43%'. Add `disabled={saving}` to the four picker Pressables (app/admin.tsx:234, 323, 327, 381) and dim them with the same `opacity: 0.6` pattern `Big` already uses at :617, so a second concurrent upload is impossible. Replace the bare `<Big label={saving ? 'Working...' : ...}>` labels with a label plus an inline `<ActivityIndicator>` inside the button. Keep the five-row Admin home exactly as it is.
**risk** DO-NOT-BREAK item 21 says Admin stays five simple rows with no wall of forms — a progress bar in the header does not add a row, but do not take this as licence to add status panels. Adding `disabled` to the pickers means an upload in flight blocks picking a different file; that is intended, but confirm a cancelled picker (`result.canceled`) still clears `saving` — it currently returns early at app/admin.tsx:205 BEFORE `setSaving(true)`, so that path is safe today and must stay that way.

## O1 — Onboarding theme screen: the crest is cropped by resizeMode="cover" — a square logo forced into a 224x124 box loses 40% of its height
**severity** high · **confidence** confirmed-in-code
**files** app/index.tsx:188, app/index.tsx:411, app/index.tsx:399, assets/images/ogn-logo-transparent.png
**root cause** The onboarding screen with the Dark/Light picker is the splash branch at app/index.tsx:181-222. The crest is rendered as `<Image source={require('../assets/images/ogn-logo-transparent.png')} resizeMode="cover" style={styles.sealImage} />` (app/index.tsx:188) where `sealImage: { width: 224, height: 124 }` (app/index.tsx:411), inside `sealWrap` which sets `overflow: 'hidden'` (app/index.tsx:399-410). I read the PNG header: the source is 614 x 614, a perfect square (aspect 1.0). `resizeMode="cover"` scales the source so it FILLS the box, using the larger scale factor: max(224/614, 124/614) = 224/614 = 0.365, giving a drawn size of 224 x 224 inside a 124-tall window. 100 of those 224 points are discarded — 50 points sliced off the top of the crest and 50 off the bottom — and `overflow: 'hidden'` hides the remainder. Any wordmark, ribbon or lower arc inside the square crest artwork is cut off at the bottom. This is purely geometric: it happens identically in dark and light theme and on every phone size, which matches the report that it is cut in both themes. Note the auth screen two taps later does this correctly — app/index.tsx:234 uses `resizeMode="contain"` on a 58x45 box (app/index.tsx:536), so the same asset is letterboxed there rather than cropped. The splash is the only place using `cover` on this asset.
**fix plan** In app/index.tsx:188 change `resizeMode="cover"` to `resizeMode="contain"`, and in styles.sealImage (app/index.tsx:411) change `{ width: 224, height: 124 }` to a square that fits the 236x150 sealWrap, e.g. `{ width: 138, height: 138 }`, so the 1:1 source is never cropped. If the ministry wants the wider plate look kept, instead give sealWrap a square aspect (e.g. width 150, height 150 at app/index.tsx:399-401) and let the logo fill it. Do not change the asset — it is the approved crest under DO-NOT-BREAK item 11. Verify by eye in BOTH themes on the splash screen, since the crest is a protected visual.
**risk** DO-NOT-BREAK item 11 protects the crest/seal as an approved visual — this change restores the full crest rather than altering it, but the block's height changes, so it shifts everything below it on the splash (which interacts with the overflow problem in NEW-1; fix both together). Item 10 requires dark and light to both work, so check both. No native module is touched, so this is OTA-safe.

**files** app/index.tsx:185, app/index.tsx:398, app/index.tsx:206, app/index.tsx:181
**root cause** The splash screen renders into a plain `Animated.View` with `style={[styles.splashInner, { paddingTop: insets.top + 40, paddingBottom: insets.bottom + 24 }]}` (app/index.tsx:185) where `splashInner: { flex: 1, alignItems: 'center', paddingHorizontal: 32 }` (app/index.tsx:398). Keep the `<View style={{ flex: 1 }} />` spacer at :206 — with flexGrow on the content container it still pushes Get Started to the bottom when there is room. Then verify at 375x667 (iPhone SE) and 430x932 (Pro Max) that the crest, the wordmark, the theme picker and the Get Started button are all fully visible.

## S3 — Story-post path: the slowest step is the base64 encode of the picked media; on top of it sit three serialized auth round trips and an awaited bookkeeping insert on the critical path
**severity** high · **confidence** confirmed-in-code
**files** lib/uploadService.ts:27, lib/uploadService.ts:46, lib/uploadAnalysis.ts:51, lib/contentService.ts:301, app/admin.tsx:224
**root cause** Timing the story path end to end, in order. Step 1, the user taps the dropzone: `ImagePicker.launchImageLibraryAsync({ mediaTypes: ['images','videos'], quality: 0.86 })` (app/admin.tsx:203) — note `quality` only affects JPEG re-encoding of images; there is no `videoQuality` and no `videoMaxDuration`, so a full-resolution phone video is taken as-is, which is what makes the payload huge. Step 2, `uploadPickedAsset` calls `await supabase.auth.getUser()` (lib/uploadService.ts:27). I confirmed in node_modules/@supabase/auth-js/dist/module/GoTrueClient.js:2548-2578 that `getUser()` with no jwt goes through `_acquireLock` and `_getUser()` to `_request(this.fetch, 'GET', ${this.url}/user, ...)` — a real network round trip, not a local read, and it runs through the app's 15 s fetch wrapper. Step 3, `readUploadBody` (lib/uploadService.ts:34) — the file read plus, downstream, the base64 encode described in the A1 finding. THIS IS THE SLOWEST STEP BY FAR and it dominates everything else; for a 40 MB video it is a ~53 MB JS string built synchronously before the upload begins. Step 4, the single PUT (lib/uploadService.ts:36-41). Step 5, `getReachableStorageUrl` (:44) — cheap, because 'story-media' is in the public set at lib/uploadService.ts:108 so `getPublicUrl` is synchronous with no network. Step 6, `await recordUploadedFile(...)` (lib/uploadService.ts:46) — this is pure bookkeeping into `uploaded_files`, yet it is awaited before the function returns the URL, and lib/uploadAnalysis.ts:51 opens it with ANOTHER `await supabase.auth.getUser()`, a second full auth round trip, followed by the insert. So two extra serialized round trips are added to the picker before the admin can even see the thumbnail, for a row nothing on this screen reads. Step 7, the user taps Post: `createAdminStory` does a THIRD `await supabase.auth.getUser()` (lib/contentService.ts:301) and then the insert (:303-317). Step 8, `await onDone()` (app/admin.tsx:224) chains up to `refresh()` and re-runs the whole seven-query `getAdminWorkbench()` before the form closes. Net: three sequential auth round trips where zero are needed (the session is already in memory), one awaited bookkeeping write that could be fire-and-forget, and a full workbench refetch gating the form's dismissal — all stacked on top of a base64 encode measured in minutes.
**fix plan** Four edits, in impact order. (1) Fix the encode — see the A1 streaming-upload plan; that is the 90% win. (2) Replace every `supabase.auth.getUser()` on a write path with `supabase.auth.getSession()`, which reads AsyncStorage with no network: lib/uploadService.ts:27 and :70, lib/uploadAnalysis.ts:51, lib/contentService.ts:301 / :335 / :369 / :275, lib/announcementsService.ts:38. Where the caller already knows the user id, pass it down instead of re-fetching — `recordUploadedFile` should take an `ownerId` argument from `uploadPickedAsset` rather than calling auth itself. (3) In lib/uploadService.ts, stop awaiting the bookkeeping write: build the return value, then fire `recordUploadedFile(...).catch((err) => console.warn('uploaded_files bookkeeping failed', err))` without await, so the picker completes as soon as the object is stored. (4) In app/admin.tsx:224 and :191-193, show the success state immediately and let `onDone()`/`refresh()` run in the background rather than awaiting it before closing the form.
**risk** getSession() does not validate the token server-side the way getUser() does, so a silently expired session would produce a storage 401 instead of a clean 'Sign in before uploading files.' — keep the explicit `if (!userId) throw new Error('Sign in before uploading files.')` guard at lib/uploadService.ts:29 and make sure an auth failure still surfaces a sign-in message (lib/errorMessages.ts:7 already maps 'jwt'/'auth'/'sign in'). Making the uploaded_files insert non-blocking means the audit row can be missing for a successful upload; that table feeds nothing the app reads today, but confirm before shipping. Do not let the un-awaited promise become an unhandled rejection.

## A4 — A newly submitted prayer request is structurally excluded from the list it is supposed to appear in: the form defaults to private, the query only returns public
**severity** high · **confidence** confirmed-in-code
**files** app/prayer.tsx:24, lib/contentService.ts:226, app/prayer.tsx:77, app/prayer.tsx:202, lib/contentService.ts:266
**root cause** app/prayer.tsx:24 sets `const [isPrivate, setIsPrivate] = useState(true)` — the privacy toggle DEFAULTS to private, and the UI reinforces it ('Share with Prayer Team', 'Your request will be kept confidential.', app/prayer.tsx:182-183). `submit()` passes that value straight through (`isPrivate` at app/prayer.tsx:64) into `submitPrayerRequest`, which inserts `is_private: input.isPrivate` (lib/contentService.ts:281). The reason it LOOKS like it worked for a moment is the optimistic prepend at app/prayer.tsx:77, `setRequests((current) => [nextRequest, ...current])` — a purely local insert that is never reconciled with the server, because `loadRequests()` is not called after a successful submit. Add `useFocusEffect(useCallback(() => { loadRequests(); }, [mode]))` from expo-router so returning to the screen re-reads. Raise the submit-mode slice at app/prayer.tsx:202 from 4 to at least 10, or drop the slice and rely on the query's `.limit(20)`. **risk** Do NOT 'fix' this by flipping the default at app/prayer.tsx:24 to public or by dropping `.eq('is_private', false)` at lib/contentService.ts:226 — either would leak confidential prayer requests to every member, and the RLS policy at supabase/rls_policies.sql:116 (`created_by = auth.uid() or is_staff_or_above() or is_private = false`) would happily serve them. DO-NOT-BREAK spec item A3 says the prayer history screen works and is liked, and 'My Requests' IS that screen — switching modes on submit changes what the user sees after submitting, so re-verify A3 by hand after this change.

## A4 — Admin side: the workbench swallows all seven query errors and is fetched once on mount, so a missing prayer request renders as "All clear"
**severity** high · **confidence** confirmed-in-code
**files** lib/adminManagementService.ts:24, lib/adminManagementService.ts:46, app/admin.tsx:73, app/admin.tsx:75, app/admin.tsx:126
**root cause** `getAdminWorkbench()` (lib/adminManagementService.ts:22-82) runs seven queries via `Promise.all` and destructures them as `[rolesResult, profilesResult, prayersResult, messagesResult, channelsResult, storiesResult, mediaResult]` (line 24). Not one of those seven results has its `.error` field read anywhere in the function. The prayer query is `supabase.from('prayer_requests').select('id, name, category, request, status, assigned_to, created_at').order('created_at', { ascending: false }).limit(40)` (line 27) — ordering and limit are correct and would show the newest — but the mapping at line 46 is `prayers: (prayersResult.data || []).map(...)`. When the query fails, `data` is null, `|| []` turns the failure into an empty list, and the failure is now indistinguishable from 'there are no prayer requests'. The screen then computes `const newPrayers = (workbench?.prayers || []).filter((p) => p.status === 'new')` (app/admin.tsx:95) and `reviewCount` (:96), and renders `{!reviewCount ? <Empty ... title="All clear" body="Nothing is waiting for you." /> : null}` (app/admin.tsx:126). So a broken read is displayed to the owner as positive confirmation that nothing needs attention. One layer up the same thing happens again: `async function refresh() { ... try { setWorkbench(await getAdminWorkbench()); } catch { /* keep what we have */ } }` (app/admin.tsx:71-74) — a totally empty catch with a comment excusing it. Because `Promise.all` rejects if ANY of the seven promises rejects, and the app's fetch wrapper aborts after 15 s (lib/supabase.ts:15, lib/requestTimeout.ts:8), one slow table takes down the entire workbench: `workbench` stays at its previous value or null, every section renders empty, and the user is told nothing. **fix plan** In lib/adminManagementService.ts:22-82, switch from `Promise.all` to `Promise.allSettled` so one failing table cannot blank the other six, and collect per-query errors into a new `errors: string[]` field on the `AdminWorkbench` type (lib/adminManagementService.ts:14-20). Check `.error` on each of the seven results and push a readable message rather than relying on `|| []`. In app/admin.tsx:71-74, replace the empty catch with state: add `const [loadError, setLoadError] = useState<string | null>(null)`, set it in the catch, and render it above the rows so a failure is visible. Change the 'All clear' Empty at app/admin.tsx:126 so it only renders when the load actually succeeded — if `errors.length` or `loadError` is set, show 'Could not load — tap to retry' instead. Add `useFocusEffect(useCallback(() => { refresh(); }, [access.userId]))` so returning to Admin re-reads, and add a RefreshControl to the Shell ScrollView at app/admin.tsx:559. Keep `run()`'s existing post-action refresh.
**risk** DO-NOT-BREAK item 21 caps Admin at five simple rows — an error banner and pull-to-refresh do not add rows, but resist growing this into a status dashboard. Item 2 role-gates Admin; the early returns at app/admin.tsx:98-108 must stay exactly as they are so a member still sees 'Admins only' rather than an error banner. `Promise.allSettled` changes the shape of the result objects — every one of the seven `.data` reads at lines 36-80 must be updated to go through `result.status === 'fulfilled' ? result.value.data : null`, or the screen will silently blank in a new way.

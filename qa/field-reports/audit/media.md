## V3 — Media tab loads once on mount and never refreshes; "videos are being prepared" is a placeholder, not a state
**severity** blocker · **confidence** confirmed-in-code
**files** app/(tabs)/messages.tsx:55, app/(tabs)/messages.tsx:62, app/(tabs)/messages.tsx:263, app/(tabs)/messages.tsx:73, app/(tabs)/messages.tsx:75, app/admin.tsx:250, lib/contentService.ts:350
**root cause** Three separate mechanisms stack up.

(1) The list loads exactly once. app/(tabs)/messages.tsx:55-62: `useEffect(() => { getMessageLibrary().then(...); getMediaItems().then(setMediaItems); getUserDownloads().then(setDownloads); }, []);` — an empty dependency array. There is no useFocusEffect, no RefreshControl and no realtime subscription in this file (grep for useFocusEffect|RefreshControl across app/, lib/, components/ hits only app/index.tsx and app/(tabs)/community.tsx). The Media tab is an expo-router tab screen that stays mounted, and /admin is a route PUSHED on top of it, so returning from admin does not remount it. The state is whatever was fetched at app launch. Only a cold start refetches — which is exactly the owner's words, 'never appeared without leaving the app'.

(2) The copy is a placeholder. The string lives at app/(tabs)/messages.tsx:263: `<EmptyState dark={dark} title="Videos are being prepared" body="New ministry videos will appear here as soon as they are published." />`, with three siblings at :239, :250 and :276. There is no processing pipeline behind it: createAdminMediaItem inserts `status: 'published'` and `published_at: new Date().toISOString()` in one shot (lib/contentService.ts:350-352), and getMediaItems reads `.eq('status','published')` (lib/contentService.ts:90). Nothing is ever 'being prepared'. The copy actively lies to the leader.

(3) Even after a restart the item can land in the wrong tab. MediaForm's kind defaults to sermon — `const [kind, setKind] = useState<MediaKind>('sermon');` (app/admin.tsx:250) — so pasting a YouTube link without tapping the 'Video' chip posts media_type='sermon'. The Videos tab filters `item.mediaType === 'video' || item.mediaType === 'live'` (app/(tabs)/messages.tsx:73) while sermons land in the Sermons list via :75. The leader then looks at Videos and still sees 'Videos are being prepared'.
**fix plan** 1) In app/(tabs)/messages.tsx extract the three fetches into a `const load = useCallback(async () => {...}, [])` and drive it from `useFocusEffect(useCallback(() => { load(); }, [load]))` (useFocusEffect is exported by expo-router) instead of the mount-only useEffect at :55. 2) Add RefreshControl to the outer ScrollView at :158 with a `refreshing` state so a leader can pull to refresh — the same pattern already used in app/(tabs)/community.tsx. 3) Rewrite the four empty-state titles at :239/:250/:263/:276 to plain truth, e.g. 'Nothing here yet' / 'Posted videos show up here' — delete 'being prepared' entirely. 4) In app/admin.tsx MediaForm, default the kind from the link: when embedUrl(link) is non-null and the leader has not tapped a chip, preselect 'video'; alternatively surface the chosen kind in the success alert at :299 ('Posted to Videos') so a mis-filed item is obvious immediately. 5) Optional belt-and-braces: after a successful post, router.push back to '/(tabs)/messages' with a param that forces the matching tab.
**risk** Refetching on every focus adds three Supabase round trips each time the user taps the Media tab; keep the 60-row limit at lib/contentService.ts:91 and consider a short in-memory cache if it feels slow on a weak connection. Do NOT change the deliberately-featured-only hero rule at app/(tabs)/messages.tsx:66-69 — the comment there records a past regression where a smoke-test upload headlined the tab for every member. DO-NOT-BREAK item 7 (Media opens audio/video in-app, documents externally) must still hold after the refactor.

## V1 — No title (or any metadata) is ever fetched from a pasted YouTube link

**root cause** lib/embed.ts is 45 lines and contains exactly three functions: fileKind (extension sniffing), embedUrl (URL rewriting) and playbackKind. embedUrl extracts ONLY the video id and rebuilds a player URL — `const id = parsed.searchParams.get('v') || (live ? live[2] : null); return id ? `https://www.youtube.com/embed/${id}?playsinline=1&autoplay=1&rel=0` : null;` (lib/embed.ts:26-27). There is no network call anywhere in the file, and a repo-wide grep for 'oembed', 'ytimg', 'img.youtube', 'hqdefault' and 'maxresdefault' across app/, lib/, components/ and supabase/ returns nothing. The admin form's title comes only from the manually typed state at app/admin.tsx:318 (`<Field ... value={title} onChange={setTitle} placeholder="Title" />`), and post() hard-rejects an empty one at app/admin.tsx:293 (`if (!title.trim()) return Alert.alert('Give it a title');`). So the leader must type the sermon title by hand, every time, exactly as observed.
**fix plan** 1) In lib/embed.ts export a new `youtubeId(url: string): string | null` that factors out the id extraction already inlined at lines 19-27 (youtu.be path segment, /live/ and /shorts/ match, ?v= param) and validates it against /^[A-Za-z0-9_-]{11}$/ — see NEW-1, which needs the same helper. 2) Add `export async function fetchLinkMeta(url)` to lib/embed.ts returning {title, author, thumbnail} | null. Show a small 'Reading the link…' hint next to the field. 4) Never gate the Post button on the fetch; if it fails the leader types the title as today.
**risk** Adds a network call to the admin form. Must not block Post when offline or when YouTube's oEmbed is slow — hence the timeout and the null fallback. Pure JS, no native module, so this is OTA-safe and does NOT trigger DO-NOT-BREAK item 22. Do not auto-overwrite a title the leader already typed, or you break the one workflow that currently works.

## V5 — YouTube embeds are configured correctly but die the moment the player sheet is minimized, while the mini bar still claims they are playing

**files** lib/nowPlaying.tsx:163, lib/nowPlaying.tsx:147, lib/nowPlaying.tsx:101, lib/nowPlaying.tsx:76, lib/nowPlaying.tsx:124, node_modules/react-native/Libraries/Modal/Modal.js:301

(<View style={styles.video}><WebView source={{ uri: embed }} allowsInlineMediaPlayback mediaPlaybackRequiresUserAction={false} allowsFullscreenVideo javaScriptEnabled style={{ backgroundColor: '#020817' }} /></View>)`. allowsInlineMediaPlayback covers iOS inline playback, mediaPlaybackRequiresUserAction={false} covers autoplay on both platforms and pairs with the `autoplay=1&playsinline=1` already in the embed URL (lib/embed.ts:27), javaScriptEnabled and domStorage default on, and app.json needs no WebView-specific entry. React Native's Modal returns null from render when it is not shown — `render() { if (!this._shouldShowModal()) { return null; } ...}` (node_modules/react-native/Libraries/Modal/Modal.js:301-303, with _shouldShowModal at :274-283 returning props.visible on Android and props.visible||state.isRendered on iOS until modalDismissed fires). Recommend (a): it matches DO-NOT-BREAK item 17 and is a five-line change. 2) Either way, fix the fake state at lib/nowPlaying.tsx:76 — for embeds derive `playing` from a real signal (injectedJavaScript posting the YouTube iframe API's onStateChange over postMessage) or set it false and label the mini bar 'Tap to reopen the video'. 3) Add music.youtube.com to the youtube host check at lib/embed.ts:23. 4) Ship NEW-1's id validation, without which a bad paste presents as 'the video will not play'.
**risk** Whether a valid link plays on the device is still worth one confirming pass on the real iPhone (build 29) — the code is correct but I have no device evidence for it. Option (b) leaves a live WebView behind every screen; watch memory and make sure it never steals touches. react-native-webview is a native module (package.json:50) but it is already in the build, and none of these edits add or remove one, so this stays OTA-shippable under DO-NOT-BREAK item 22. ## NEW-1 — embedUrl never validates the video id, so a malformed or doubled paste passes the admin link check and posts a dead embed

**risk** Tightening validation can reject a link shape that works today — test the six shapes above before shipping, especially the /embed/ passthrough at lib/embed.ts:24 and the ?si= share parameter, both of which I verified still resolve correctly.

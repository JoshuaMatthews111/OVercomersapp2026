## NEW-1 — Map screen calls two useMemo hooks below three early returns — React throws as soon as regions load

**files** app/maps.native.tsx:340, app/maps.native.tsx:355, app/maps.native.tsx:362, app/maps.native.tsx:376, lib/accessControl.ts:115

Commit d85c899 added the two GeoJSON useMemos in the wrong place. There is no ErrorBoundary or componentDidCatch anywhere in app/ or components/, so nothing catches it.

Moving regionShape above the gate means it now runs for users who fail the canUseEvangelism check (DO-NOT-BREAK #2, role gating) — that is fine, it computes a JS object and renders nothing, but do not move any data fetch along with it. ## NEW-2 — Every map tap is a no-op: handler reads event.geometry.coordinates, MapLibre v11 emits {lngLat, point}
**severity** blocker · **confidence** confirmed-in-code
**files** app/maps.native.tsx:384, app/maps.native.tsx:403, app/maps.native.tsx:279, node_modules/@maplibre/maplibre-react-native/src/types/PressEvent.ts:6, node_modules/@maplibre/maplibre-react-native/ios/components/map-view/MLRNMapViewComponentView.mm:99
**root cause** app/maps.native.tsx:384-386 is `function onMapPress(event: {...} | any) { const coords: [number, number] | undefined = event?.geometry?.coordinates; if (!coords) return; }`, wired at 403 as `onPress={(e: any) => onMapPress(e?.nativeEvent)}`. In @maplibre/maplibre-react-native 11.3.10 the press payload is `interface PressEvent { lngLat: LngLat; point: PixelPoint }` (src/types/PressEvent.ts:6-20) — there is no `geometry` key. The Fabric component view confirms it at the native layer: `MLRNMapViewEventEmitter::OnPress eventStruct{pressEvent.lngLat, pressEvent.point}` (ios/components/map-view/MLRNMapViewComponentView.mm:99-100), built from `dict[@"properties"][@"lngLat"]` (same file, lines 24-27). Only the legacy paper path sends a full GeoJSON Feature with a geometry key (ios/components/map-view/MLRNMapTouchEvent.m:32, `return [feature geoJSONDictionary]`), and this app is Expo SDK 57 / react-native 0.86.3 with no `newArchEnabled` opt-out in app.json, i.e. New Architecture. So `coords` is always undefined and the function returns immediately. Consequences: (1) tap-to-select a drawn region never fires — the point-in-polygon loop at 389-391 is unreachable; (2) draw-by-hand never records a corner — `if (drawing) { setDrawing([...drawing, point]); return; }` at 388 is unreachable, so the toolbar reads "…0 so far" forever and Save always hits `if (!selected || !drawing || drawing.length < 3) return Alert.alert('Tap at least three corners')` at 279. TypeScript did not catch it because the parameter is typed `{...} | any`, which collapses to any, and the handler is cast `(e: any)`. Before the migration the same screen used react-native-maps' `event.nativeEvent.coordinate` and did region selection via a Polygon onPress prop (git show d85c899^:app/maps.native.tsx:328 and :338), so both paths worked and both regressed in d85c899.
**fix plan** In app/maps.native.tsx:384-387 read the documented shape: `const lngLat: [number, number] | undefined = event?.lngLat; if (!lngLat) return; const point: LatLng = { latitude: lngLat[1], longitude: lngLat[0] };` Leave the rest of onMapPress (the drawing branch at 388 and the point-in-polygon loop at 389-391) untouched. Drop the `| any` from the parameter type and type it `NativeSyntheticEvent<PressEvent>['nativeEvent']` (PressEvent is exported from @maplibre/maplibre-react-native) so a future payload change fails typecheck instead of failing silently. While there, consider also typing the onPress prop at 403 rather than casting to any.
**risk** Touches two DO-NOT-BREAK Map engine behaviours directly ("Tap a drawn region to select it (JS point-in-polygon on the tap point)" and "Draw an outline by tapping corners; undo, cancel, save"), so it must be re-verified on device, not assumed: tap inside a drawn region and confirm the sheet switches to it, then draw a 3-corner outline and save it. Do not change the stored {latitude, longitude} shape — convert at the MapLibre edge only, as the last Map engine bullet requires. Blocked behind NEW-1: until the hook crash is fixed you cannot reach the map to test this.

## M2 — Map opens on the seeded United States overview because first load reads location permission without ever asking for it
**severity** high · **confidence** confirmed-in-code
**files** app/maps.native.tsx:131, app/maps.native.tsx:133, app/maps.native.tsx:119, app/maps.native.tsx:402, app/maps.native.tsx:406, app/maps.native.tsx:174, node_modules/@maplibre/maplibre-react-native/ios/modules/location/MLRNLocationManager.m:44
**root cause** Four things combine. (1) The first-load effect calls the non-prompting getter: `const perm = await Location.getForegroundPermissionsAsync(); const status = perm.status; if (status !== 'granted') return;` (maps.native.tsx:131-133). On a fresh install status is 'undetermined', so the whole location branch is skipped and no dialog is ever shown by the app. (2) The camera handler you asked me to quote is `onDidFinishLoadingMap={() => flyTo(selected.center, deltaToZoom(levelDelta[selected.level]), 0)}` (line 402) — an instant jump (duration 0) to whatever `selected` happens to be. (3) `selected` defaults in loadAll to `territories.find((t) => t.level !== 'global') || territories[0]` (line 119), which in seed order is 'United States' — level 'country', center POINT(-98.5795 39.8283) (supabase/seed.sql:39-41). levelDelta.country is 18 (line 74) and deltaToZoom(18) = round(log2(360/18)) = round(4.32) = 4. Zoom 4 over Kansas is exactly the wide US overview the owner saw; the top contentInset of insets.top+110 (line 400) pushes that center low on screen, which is why the old note at line 124-125 describes it as "centered on Canada". (4) Meanwhile `<UserLocation />` (line 406) starts MapLibre's own location manager, which DOES prompt: `[self->locationManager requestWhenInUseAuthorization]` (ios/modules/location/MLRNLocationManager.m:44 and :73). So the user sees a location prompt, grants it, gets a blue dot — and the camera never moves, because the app's own branch already gave up. Even when permission is already granted there is a race: the style-load handler at 402 and the user-location `flyTo(openedOnMe, deltaToZoom(0.03), 700)` at line 174 are unordered, and nothing guards 402, so a slow style load stomps the camera back to the country view after it had reached the user.
**fix plan** Three edits in app/maps.native.tsx. (a) Line 131: swap the non-prompting getter for the prompting one — `const perm = await Location.requestForegroundPermissionsAsync();`. The permission plumbing is already in place: NSLocationWhenInUseUsageDescription at app.json:14, ACCESS_FINE_LOCATION and ACCESS_COARSE_LOCATION at app.json:27-28, and the expo-location config plugin at app.json:44, so no native change and no new build flag is needed beyond the normal EAS build. (b) Kill the race with a ref: add `const openedOnUserRef = useRef(false);` next to the other refs at 85-87; set it true in the openedOnMe effect right before line 174's flyTo; and guard the handler at 402 as `onDidFinishLoadingMap={() => { if (openedOnUserRef.current) return; flyTo(selected.center, deltaToZoom(levelDelta[selected.level]), 0); }}`. That makes the outcome order-independent in both directions. (c) Denial path: keep the first-load branch silent (no alert on open is correct) and fall back to the current selected-territory camera; the explicit my-location button stays the recovery route — it already calls `Location.requestForegroundPermissionsAsync()` at line 216 and alerts at 217. Improve 217 for the permanent-denial case: requestForegroundPermissionsAsync returns `{ status: 'denied', canAskAgain: false }` once the user has refused, and the current alert then tells them to "turn on location" with no way to do it — add a second button calling Linking.openSettings(). A provider-native alternative to (b) exists — Camera accepts `trackUserLocation="default"` (node_modules/@maplibre/maplibre-react-native/src/components/camera/Camera.tsx:261) — but it fights the manual flyTo calls used by search and fit-to-region, so I recommend the guard-ref, which is the smaller change.
**risk** Adding a permission prompt to first open of the Evangelism Dashboard changes what a leader sees on launch; if it is refused the map stays on the fallback camera, so verify the denied path explicitly and not just the granted one. DO-NOT-BREAK Map engine requires "My location" to keep working — re-verify the button at line 451 after the change, since both paths now call requestForegroundPermissionsAsync. Blocked behind NEW-1 and NEW-2 for any on-device verification.

## NEW-3 — Outreach contact pins vanish after reload: location is written as WKT but read back as PostGIS hex, and the regex never matches
**severity** high · **confidence** confirmed-in-code
**files** lib/evangelismService.ts:158, lib/evangelismService.ts:179, lib/evangelismService.ts:273, supabase/schema.sql:159, app/maps.native.tsx:306, app/maps.native.tsx:421
**root cause** saveOutreachContact writes `const location = input.location ? \`POINT(${input.location.longitude} ${input.location.latitude})\` : null;` (lib/evangelismService.ts:179) into `location geography(Point, 4326)` (supabase/schema.sql:159) — PostGIS parses that WKT on insert, so the write is fine. The read is not: getOutreachContacts does `supabase.from('outreach_contacts').select('*')` (evangelismService.ts:147) and maps `location: extractPoint(row.location) || undefined` (line 158). PostgREST serialises a geography column using its default text output, which is hex EWKB ("0101000020E6100000..."), not "POINT(x y)". extractPoint (lines 273-280) only accepts an object with a numeric .latitude, or a string matching /POINT\((-?\d+\.?\d*) (-?\d+\.?\d*)\)/ — the hex string matches neither, so it returns null and every contact comes back with location undefined. The marker render is guarded on exactly that field: `{relatedContacts.map((c) => c.location ? (<Marker .../>) : null)}` (app/maps.native.tsx:421-425), so no contact dot ever draws after a reload. It looks like it works at save time only because addRecord optimistically unshifts a local object carrying `location: myLocation || selected.center` (maps.native.tsx:306-312) — the pin appears, then disappears the next time the screen loads. The territories path was given a dedicated RPC (territories_geo) precisely to avoid this; outreach_contacts never got one.
**fix plan** Mirror the territories fix. Either (a) add an RPC alongside territories_geo — `outreach_contacts_geo()` returning st_y(location::geometry) as location_lat and st_x(location::geometry) as location_lng plus the other columns — and have getOutreachContacts call it with the current select('*') as the fallback, exactly the shape getTerritories already uses at evangelismService.ts:49-54; or (b) if you want no new RPC, add plain `location_lat double precision` / `location_lng double precision` columns, write them alongside the geography in saveOutreachContact (line 179-201), and read them in the mapper at line 158. Option (a) keeps the geography column authoritative and matches the existing pattern; option (b) is a migration but needs no function. Either way, leave extractPoint in place as the fallback so nothing else that calls it breaks. Verify by adding a record from the Add record tab, backing out of the screen, reopening it, and confirming the dot is still on the map.
**risk** Both options require a database change against the live project, so this is not an app-only fix. Whatever you do, keep the stored client-side shape as {latitude, longitude} and convert to [lng, lat] only at the MapLibre boundary (DO-NOT-BREAK Map engine, last bullet). Do not change the write format in saveOutreachContact while the read is still regex-based, or you will break both halves at once.

## stories

STORIES audit of /Volumes/mindfulssd/dev/OVercomersapp2026. Read-only: no files changed, no git state touched, no builds run. Covered S1-S12 and H4, plus O1 (the onboarding clipping the owner asked about directly) because it shares a root cause with S10.

The story feature has four structural faults, not twelve separate bugs.

1. Home never refetches. app/(tabs)/index.tsx:74-77 loads stories once on mount with useEffect(..., []). No useFocusEffect, no RefreshControl, no realtime .channel() on app_stories - even though the table IS in the realtime publication (supabase/app_feature_expansion.sql:370) and the refresh pattern already exists in this app at app/(tabs)/community.tsx:90. Home stays mounted across tab switches and across a push to /admin, so a post or a delete is invisible until a full app restart. This alone explains S1, S11 and the Home half of S12. A 60-second setInterval (index.tsx:82-85) re-renders and re-filters the stale array, which makes the screen look live while serving old data.

2. The upload path is the slowest possible shape. lib/uploadBody.ts:10 reads the whole file into a JS ArrayBuffer, then React Native base64-encodes that entire buffer on the JS thread before it crosses the bridge (node_modules/react-native/Libraries/Network/convertRequestBody.js:38-41). No chunking, no resumable upload, no progress callback, and all of that work happens outside the 120s storage timeout in lib/supabase.ts:15. Three separate supabase.auth.getUser() round trips run per story post. That is S3, and it also drives A1.

3. Two hard clips from one third-party native view. expo-linear-gradient's iOS backing layer sets masksToBounds = true unconditionally (node_modules/expo-linear-gradient/ios/LinearGradientLayer.swift:20 and :26), so a LinearGradient always clips its children no matter what overflow says. The story ring badge sits at left:-6, bottom:-3 outside those bounds (index.tsx:439) - that is S10, in both themes, exactly as reported. The onboarding splash is wrapped in the same component (app/index.tsx:183) with no ScrollView, which clips overflow on short phones - part of O1.

4. Client role gates and Postgres RLS disagree. lib/accessControl.ts:50 grants canManageContent to super_admin, admin, staff and media_admin. The server requires is_staff_or_above() - staff, leader, admin, super_admin (supabase/rls_policies.sql:28-31) - on both the app_stories policy (app_feature_expansion.sql:192-194) and the storage insert policy (:327). media_admin and moderator therefore get the full Admin posting UI and are refused by the database. Members are locked out at both layers, which is S7/H4.

Two things the owner did not raise that are worse than they look: the sensitive-content filter that DO-NOT-BREAK.md item 18 says lives in the database does not exist anywhere in supabase/ (S8 is unimplemented, and every story publishes straight to status published), and the story-media bucket rejects video/quicktime, which is the actual mime type of most iPhone videos (S6).

Confidence notes: everything marked confirmed-in-code was read in the file cited. The one item I could not settle from the repo is whether the live app_stories table has a DEFAULT on expires_at - that column appears in no SQL in this repo at all, yet the app filters on it. I flagged that as the second, independent cause of S1/S11 with the exact one-line DB query that settles it.

## chat

CHAT audit, read-only, no files touched. All six spec ids covered plus five nearby defects and the onboarding item the owner raised directly.

C1 is the one to fix first, and the mechanism is not in the Chat screen. I ruled out every suspect inside app/(tabs)/community.tsx: no router call at module scope or in a render body, no setState during render, no component defined inside another render, no per-render key, no synchronous work on focus, and no Updates.reloadAsync or ErrorBoundary anywhere in app/ lib/ components/. What I did find is a four-link chain that turns any single auth event carrying a null session into a full application rebuild: app/_layout.tsx:32 sets session from every event without looking at the event name; app/_layout.tsx:60 keys NowPlayingProvider on the session user id, so the key flips to 'signed-out' and destroys the whole tree below it; app/_layout.tsx:66 unmounts (tabs) a second way via Stack.Protected; app/(tabs)/_layout.tsx:74 navigates to /welcome. Then app/welcome.tsx:9 turns out to be `export { default } from './index'` — /welcome IS the splash screen — and its useFocusEffect at app/index.tsx:55-68 immediately replaces back to /(tabs), which remounts the tab layout into its full-screen "Loading your OGN home..." state and lands on Home. Splash, spinner, back to Home. That is the reload the owner sees.

What makes Chat the trigger, ranked: the Chat tab is the only tab that opens a Supabase Realtime websocket (announcementsService.ts:57, reached from community.tsx:59 — I grepped every .channel( call site to confirm), and authenticating that socket forces a session refresh that, if it fails, makes GoTrue emit SIGNED_OUT; second, mounting the tab fires two extra /auth/v1/user round trips through useAccessProfile; third and least likely, a fatal JS error recovered by expo-updates. I would fix the teardown chain regardless of trigger, since it converts any token hiccup anywhere in the app into a restart.

C2 is not broken, it was never built. No insert into chat_channels exists in the entire app — only two SELECTs. The Chat tab's empty state tells the member to start a DM from a person's profile, and app/person.tsx:105-113 is a non-pressable View reading "Direct messages come next." Notably the backend is already finished: app_feature_expansion.sql:282 lets any authenticated member create a direct or group channel, and :291 lets the creator add the other person. Client work only.

C3/C4 are both fully confirmed. Nothing resizes the photo — expo-image-picker's quality only re-encodes — and lib/uploadBody.ts:10 reads the entire file into the JS heap before uploading, with no progress callback, so a 4 MB original crawls up and the UI shows a bare spinner. The crop is one style property: ChatAttachments.tsx:214 `aspectRatio: 1` on a 220 pt box combined with contentFit="cover" at :148, while the picker preview at :111 uses contentFit="contain". The member approves the whole frame and the bubble then centre-crops it. The picker already captures the true width/height and the code throws them away.

C5: three gates at 50 MB, and the third is the bucket itself — chat-attachments is 52428800 bytes in app_feature_expansion.sql:314, and the 2026-09-18 migration restates "Preserve the private bucket and 50 MiB limit". release_hardening.sql raised only app-assets. So lifting the client cap alone changes nothing. No compression package of any kind is installed; a one-minute 1080p clip is ~130 MB, so compression is required, not optional, and it means a new EAS build.

C6 works and the RLS backs it up (public self-join at rls_policies.sql:91), but every single send pays an extra membership SELECT plus a .single() INSERT that throws on a duplicate race, surfacing as "Message not sent" on a healthy connection.

The most valuable thing I found that the owner did not report is NEW-1: app/chat-room.tsx:93 loads messages and the member roster in one Promise.all, so if the get_chat_member_roster RPC fails — and that migration is dated the very day of the device run — the successfully loaded messages are discarded and the room reads "No messages yet". Worth checking whether both 2026-09-18 migrations are actually applied to the live project before any client work.

O1, which the owner asked about directly, is the splash at app/index.tsx:181-223. Two independent clipping causes: the 614x614 crest is drawn with resizeMode="cover" into a 224x124 box (:188, :411), which shears exactly 100 px off the top and bottom of the crest; and the column has no ScrollView at all, with roughly 885 pt of fixed-height content against window heights of 667 (SE), 812, 852 and 932, so on every iPhone but the Pro Max the bottom simply runs off the edge with nothing able to scroll it back. The one-word fix is cover to contain; the layout fix is a ScrollView with flexGrow. Note app/index.tsx:29 also reads Dimensions.get('window') once at module scope, which is stale after rotation.

## admin

AUDIT SCOPE: Admin + Prayer (A1, A2, A3, A4, S3-admin-half, general slowness). Read-only — nothing was edited, no git state changed, no builds run.

I led the findings with the screen you actually asked about (O1, the onboarding page with the Dark/Light theme picker), because that is a direct question and I found two confirmed causes in code. It sits in app/index.tsx, outside my assigned area, so whoever owns Onboarding should own the fix — but the mechanism is settled and quoted below so it does not need re-investigating.

HEADLINE FOR MY OWN AREA (A1 / S3): the slowness is not the network and not Supabase. lib/uploadBody.ts reads the entire picked file into a JavaScript ArrayBuffer, and React Native then base64-encodes that whole buffer in pure JavaScript on the JS thread before a single byte leaves the phone (node_modules/react-native/Libraries/Network/convertRequestBody.js:38-41 — `return {base64: binaryToBase64(body)}`, and binaryToBase64.js calls base64-js `fromByteArray`, a synchronous JS loop). A 40 MB phone video becomes a ~53 MB JavaScript string built byte by byte, then crosses the bridge as a string, then is decoded natively, then uploaded as one non-resumable PUT with no progress events. That fully accounts for the 5-10 minutes with a frozen UI. The good news: expo-file-system 57 is already a dependency and already ships `File.upload()` / `File.createUploadTask(url, { onProgress })` with native streaming and real progress, so the fix needs no new native module and no dependency change (relevant to DO-NOT-BREAK item 22).

ON TOP OF THAT, the admin post forms show no progress at all. The Shell spinner at app/admin.tsx:557 is driven only by `busy`, which only `run()` at :81/:89 ever sets. StoryForm, MediaForm, EventForm and NoticePage each keep their own private `saving`/`sending` state that never reaches Shell, so during the slowest operation in the app the header spinner is guaranteed not to spin. The only feedback is the submit button's label changing to "Working...".

A4 HAS TWO SEPARATE CAUSES, one on each side. On the member side, app/prayer.tsx defaults `isPrivate = true` (:24) while `getPrayerRequests()` filters `.eq('is_private', false)` — so a newly submitted request is structurally excluded from the list it is supposed to appear in; the only reason it seems to appear is an optimistic local prepend at :77 that is lost on the next load. On the admin side, `getAdminWorkbench()` never reads `.error` on any of its seven queries and `refresh()`'s catch is empty (app/admin.tsx:73), so a failed or timed-out prayer query renders the screen as "All clear" — and the workbench is fetched once on mount with no `useFocusEffect`, so a request submitted after Admin opened never shows up.

A2 AND A3 BOTH WORK TODAY and I am not proposing behaviour changes to them. Both carry a dated fragility worth recording: the push path has a 15 s client timeout (lib/supabase.ts:15) against an edge function whose exp.host chunk loop is sequential and unbounded, and the announcement row is written before the push, so one timeout plus one retry produces two announcements and two pushes. Prayer history has no try/catch on its loader and a `status[0]` index that crashes on a null status.

ERROR SWALLOWING — the direct answer to "nothing happening": app/admin.tsx:73 (empty catch on the whole workbench), lib/adminManagementService.ts:24-34 (seven queries, zero error checks), app/admin.tsx:407 (`.catch(() => undefined)` on people search), lib/adminService.ts:77 (`if (error) return 0`), and across lib/contentService.ts lines 16/47/69/92/211/230/253 — of which :230 is the worst, because a failed prayer read returns the hard-coded mock array from data/mockData.ts, showing fabricated prayer requests ("Alicia", "Michael") as if they were real.

CONFIDENCE: everything below is read in code except the two device-check items, which I have flagged as such rather than asserted.

## theme

THEMING AND VISUAL POLISH — read-only audit, no files changed.

THE ONE-LINE DIAGNOSIS FOR T1: the app has no dark palette. lib/theme.ts exports a single light-biased `colors` object (28 literals) and nothing else that varies by mode. Dark mode was therefore built by hand, inline, screen by screen — 158 `*Dark:` style overrides across the six tab screens alone, each one a deliberate design decision (frosted white@6% fills, gold rims at 0.2-0.72 alpha, tinted inputs). ## upload-pipeline

UPLOAD AND NETWORK PIPELINE — read-only audit, no files changed.

ONE PHOTO UPLOAD, END TO END (admin story is the worst case):
1. app/admin.tsx:203 `ImagePicker.launchImageLibraryAsync({ mediaTypes:['images','videos'], quality: 0.86 })`. `quality` re-encodes JPEG but does NOT resize — a 12 MP photo stays 12 MP (~3-5 MB).
2. lib/uploadService.ts:27 `await supabase.auth.getUser()` — a NETWORK round trip (auth-js GoTrueClient.js:2590 does `GET ${url}/user`), plus an auth-lock acquire.
3. lib/uploadService.ts:34 -> lib/uploadBody.ts:8-13:
     const file = new File(uri);
     if (file.size > maxBytes) throw new Error('Choose a file smaller than 50 MB.');
     const body = await file.arrayBuffer();
   `File.arrayBuffer()` (node_modules/expo-file-system/src/File.ts:186-189) is `(await this.bytes()).buffer` — the ENTIRE file lands in one JS ArrayBuffer. Copy #1.
4. lib/uploadService.ts:36-41 hands that ArrayBuffer to `supabase.storage.from(...).upload(...)`. storage-js 2.108.1 `uploadOrUpdate` only wraps Blob/FormData; an ArrayBuffer is passed straight through as `init.body`.

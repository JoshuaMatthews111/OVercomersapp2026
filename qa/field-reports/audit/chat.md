## C1 — Chat tab "reloads the whole app": any momentary null session tears down and rebuilds the entire tree, and /welcome bounces straight back into the tabs
**severity** blocker · **confidence** likely
**files** app/_layout.tsx:60, app/_layout.tsx:32, app/_layout.tsx:66, app/(tabs)/_layout.tsx:72, app/welcome.tsx:9, app/index.tsx:55, app/(tabs)/community.tsx:59, lib/accessControl.ts:130
**root cause** I ruled out every mechanism in the Chat screen itself. app/(tabs)/community.tsx has no router call at module scope or in a render body, no setState during render, no component defined inside another render, no key that changes per render, and no synchronous work on focus; grep over app/ lib/ components/ finds no Updates.reloadAsync, no expo-updates import, and no ErrorBoundary anywhere. The reload is not in the Chat screen — it is the app's reaction to a single auth event, and the Chat tab is what provokes that event.

The teardown machinery is confirmed in code, four pieces in a chain:
1. app/_layout.tsx:32 `const { data } = supabase.auth.onAuthStateChange((_event, next) => { authChanged = true; finish(next); });` — `finish` calls `setSession(next)` for EVERY event, and never looks at `_event`. Any event carrying a null session (SIGNED_OUT emitted by supabase-js when a token refresh or a /auth/v1/user call fails) sets session to null.
2. app/_layout.tsx:60 `<NowPlayingProvider key={session?.user.id || 'signed-out'}>` — the key flips to 'signed-out', which unmounts and rebuilds the ENTIRE tree below it, Stack included. This alone is a literal full-app remount (and kills background audio, DO-NOT-BREAK #17).
3. app/_layout.tsx:66 `<Stack.Protected guard={Boolean(session)}>` — the (tabs) screen is unmounted a second way.
4. app/(tabs)/_layout.tsx:72-75 `supabase.auth.onAuthStateChange((_event, session) => { if (!session) router.replace('/welcome'); })` — also ignores `_event` and navigates away.
Then the bounce: app/welcome.tsx:9 is `export { default } from './index';` — /welcome IS the splash screen (crest, wordmark, fade-in). Its app/index.tsx:55-68 `useFocusEffect` calls `supabase.auth.getSession()` and, because the session is still in AsyncStorage, immediately `router.replace('/(tabs)')`. (tabs)/_layout.tsx then remounts with `checkingSession` true and paints the full-screen "Loading your OGN home..." (line 83-90) before rendering Tabs at the initial route, Home.
Observed result: press Chat -> OGN splash -> "Loading your OGN home..." -> back on Home. Indistinguishable from an app reload.

What makes the Chat tab the trigger (ranked):
(a) Most likely. app/(tabs)/community.tsx:59 `const stop = subscribeToAnnouncements(...)` -> lib/announcementsService.ts:56-62 `supabase.channel('announcements-feed').subscribe()`. Grepping `.channel(` across app/ lib/ components/ gives exactly three call sites: chatService.ts:210 (inside a room, not a tab), evangelismService.ts:139 (not a tab), announcementsService.ts:57 (community.tsx only). The Chat tab is the ONLY tab that opens a Supabase Realtime websocket. supabase-js authenticates that socket by resolving the access token through auth, which forces a session read/refresh; a refresh that fails makes GoTrue remove the session and emit SIGNED_OUT with a null session, which is exactly the event the chain above over-reacts to. Note lib/supabase.ts:15 aborts any non-storage request at 15 s via fetchWithTimeout, so a slow network turns a refresh into a failure rather than a retry.
(b) Second. Mounting the tab fires two extra /auth/v1/user round trips: lib/accessControl.ts:130 `refreshAccess(revision)` runs immediately, and the `onAuthStateChange` registration at :131 makes supabase-js deliver INITIAL_SESSION to the new subscriber, which schedules a second `refreshAccess` at :136. Each one is `supabase.auth.getUser()` (accessControl.ts:69), a network call that signs the user out on a 401/403. This is weaker than (a) because Home (app/(tabs)/index.tsx:68) uses the same hook and does not reload — but Home mounts at launch with a fresh token, Chat mounts minutes later with a stale one.
(c) Third, and mutually exclusive with (a)/(b). A fatal JS error on mount. There is no ErrorBoundary in the repo, and expo-updates is a dependency (package.json) with app.json:94-97 configuring an updates URL, so in a TestFlight build a fatal JS error relaunches the app instead of showing a redbox. I found no throwing code path on this screen, so I rank this last.

I would fix the teardown chain first regardless of which trigger it is: it converts a recoverable token hiccup anywhere in the app into a full restart.
**fix plan** Fix the reaction, not just the trigger.
1. app/_layout.tsx:32-35 — use the event, not the session: only `SIGNED_OUT` and `USER_DELETED` may set session to null. Ignore null sessions arriving on TOKEN_REFRESHED / INITIAL_SESSION / USER_UPDATED (keep the previous session).
2. app/_layout.tsx:60 — drop the dynamic key on NowPlayingProvider, or hold the user id in a ref that changes only on a confirmed SIGNED_OUT. Rekeying is what rebuilds the whole tree.
3. app/(tabs)/_layout.tsx:72-75 — same guard: `if (_event === 'SIGNED_OUT') router.replace('/welcome')`.
4. app/welcome.tsx:9 / app/index.tsx:55-68 — /welcome must not auto-replace back to /(tabs). Give welcome its own component, or pass a param from the sign-out path that suppresses the useFocusEffect redirect, so a sign-out lands and stays.
5. lib/accessControl.ts:113-144 — collapse the seven useAccessProfile call sites (admin, maps, maps.native, chat-room, (tabs)/index, (tabs)/community, (tabs)/messages, (tabs)/profile) into one provider mounted once in app/_layout.tsx, so mounting a tab costs zero extra /auth/v1/user calls and one auth subscription exists instead of eight.
6. app/(tabs)/community.tsx:57-61 — open the realtime channel only after the first successful `load()` resolves, not synchronously on mount, so the socket never races a token refresh during the tab transition.
Instrument before shipping: log every onAuthStateChange `_event` to the device console so the next device run names the event that fires on the Chat tap.
**risk** DO-NOT-BREAK #3 (no unauthenticated access beyond onboarding, sign-in, create-account) — the guard must still send a genuinely signed-out user to welcome; only the definition of "signed out" changes. DO-NOT-BREAK #17 (one NowPlayingProvider above the whole app) — removing the key is required by #17's spirit, but verify background audio survives sign-in/sign-out. DO-NOT-BREAK #1 (six tabs in order) is untouched. Re-verify: sign out from More (app/(tabs)/profile.tsx:125) still lands on welcome and cannot be back-navigated into the tabs.

## C3 — Photo send is slow: the full-resolution original is uploaded, and the whole file is first read into the JS heap as an ArrayBuffer
**severity** high · **confidence** confirmed-in-code
**files** components/ChatAttachments.tsx:37, components/ChatAttachments.tsx:40, lib/uploadBody.ts:8, lib/chatService.ts:88, app/chat-room.tsx:172
**root cause** Nothing resizes or compresses the image. components/ChatAttachments.tsx:40-45 `ImagePicker.launchImageLibraryAsync({ mediaTypes: ['images'], quality: 0.85, ... })` — expo-image-picker has no resize option; `quality` only re-encodes JPEG, it does not reduce dimensions. A current iPhone photo stays ~4032x3024, roughly 3-5 MB, and that is what gets uploaded for a bubble that renders 220 pt wide (ChatAttachments.tsx:214).
Then the upload path doubles the cost. lib/uploadBody.ts:8-13: `const file = new File(uri); ... const body = await file.arrayBuffer();` reads the ENTIRE file into JavaScript memory before a single byte goes out, then hands the buffer to lib/chatService.ts:89 `supabase.storage.from(ATTACHMENT_BUCKET).upload(path, upload.body, ...)`, which copies it again for the fetch body. There is no streaming, no resumable upload, no progress callback — so app/chat-room.tsx:172-190 `sendAttachment` can only show a spinner (ChatAttachments.tsx:131) with no percentage, which is why it reads as hung rather than slow.
`npm ls` / node_modules confirm neither expo-image-manipulator nor any video/image compressor is installed (package.json dependencies list has expo-image-picker, expo-image, expo-video, expo-file-system and no manipulator).
**fix plan** 1. Add expo-image-manipulator and, in components/ChatAttachments.tsx `pick()` (line 26-51), after the picker returns an image, resize to a max edge of ~1600 px and re-encode JPEG at ~0.8 before returning the PickedFile. That alone takes a typical send from ~4 MB to ~300 KB. Keep the ORIGINAL width/height on PickedFile (already captured at :50) so C4 can use the true aspect ratio.
2. lib/uploadBody.ts — for files above a few MB, stop materialising an ArrayBuffer. Use expo-file-system's upload API (or a FormData/file-URI body) so the bytes stream from disk; keep the current path only for the web branch (:15-20).
3. Thread progress through: give uploadChatAttachment (lib/chatService.ts:80) an onProgress callback and render a percentage in the AttachmentPreview send button (ChatAttachments.tsx:130-132) instead of a bare ActivityIndicator.
**risk** expo-image-manipulator is a native module, so per DO-NOT-BREAK #22 this ships as a NEW EAS BUILD, not an OTA update. Changing the upload body type risks breaking the storage policy path `<room>/<user>/` (DO-NOT-BREAK #20) and the bucket's allowed_mime_types — re-encoding to JPEG must keep contentType 'image/jpeg', which the bucket allows. There is a unit test at qa/upload-body.test.mjs that covers readUploadBody; keep it passing.

## C4 — Sent photo is cropped in the bubble: a square box plus contentFit="cover" centre-crops every non-square photo
**severity** high · **confidence** confirmed-in-code
**files** components/ChatAttachments.tsx:214, components/ChatAttachments.tsx:148, components/ChatAttachments.tsx:111
**root cause** The style property responsible is `aspectRatio: 1`.
components/ChatAttachments.tsx:214 — `image: { width: 220, maxWidth: '100%', aspectRatio: 1 },`
components/ChatAttachments.tsx:148 — `<Image source={{ uri: attachment.url }} contentFit="cover" transition={150} style={styles.image} cachePolicy="memory-disk" />`
The bubble box is forced to 220x220. `contentFit="cover"` scales the photo until it fills that box and throws away the overflow. A 4:3 landscape phone photo loses 25% off each side; a 3:4 portrait photo loses 25% off the top and 25% off the bottom (heads and feet).
The picker preview does the opposite, which is why they do not match: ChatAttachments.tsx:111 `<Image source={{ uri: file.uri }} contentFit="contain" style={styles.previewImage} />` with `previewImage: { width: '100%', height: '100%' }` (:206) inside `previewStage: { flex: 1, alignItems: 'center', justifyContent: 'center' }` (:205). contain letterboxes and shows the whole frame. So the member approves the full photo and the bubble then crops it.
The real dimensions are available and thrown away: PickedFile already carries `width`/`height` (ChatAttachments.tsx:16, populated at :50 from the picker asset), but uploadChatAttachment (lib/chatService.ts:80-92) never stores them and ChatAttachment (chatService.ts:10-16) has no width/height field, so the bubble has nothing to size itself from.
**fix plan** 1. Persist the dimensions: add `attachment_width` / `attachment_height` integer columns to chat_messages in a new migration, add `width?`/`height?` to the ChatAttachment type (lib/chatService.ts:10-16), pass them from PickedFile through uploadChatAttachment (:80) and sendChatMessage (:168-190), and map them in rowAttachment (:65-76) and subscribeToChat (:232).
2. components/ChatAttachments.tsx:214 — replace the fixed `aspectRatio: 1` with the real ratio, clamped so a very tall photo does not take over the thread: `aspectRatio: clamp(width / height, 0.6, 1.8)`.
3. For messages already in the database with no stored dimensions, fall back to expo-image's `onLoad` event (it reports `source.width`/`source.height`) and set the ratio in state; until it fires use 4:3, not 1:1.
4. Keep `contentFit="cover"` only after the ratio is correct (it then crops nothing); if you prefer zero risk, use `contentFit="contain"` with a background, which can never crop.
**risk** A new migration touches chat_messages, which carries the server-side sensitive-content filter triggers (DO-NOT-BREAK #18) — add columns only, do not drop or recreate the table or its triggers. Taller bubbles change thread layout; check the inverted FlatList in app/chat-room.tsx:341-359 still scrolls to the newest message. DO-NOT-BREAK #20 (inline photo/video bubbles) must still render for existing messages that have no stored dimensions.

## C5 — 50 MB video cap is enforced in three places including the Supabase bucket itself; raising the client cap alone will not send a one-minute phone video
**severity** high · **confidence** confirmed-in-code
**files** lib/uploadBody.ts:6, lib/uploadBody.ts:9, components/ChatAttachments.tsx:63, supabase/app_feature_expansion.sql:314, supabase/migrations/20260918093000_chat_phone_attachment_formats.sql:1, supabase/release_hardening.sql:59
**root cause** Three independent 50 MB gates, and the third is server-side.
1. components/ChatAttachments.tsx:63 — `if (file.size && file.size > 50 * 1024 * 1024) return Alert.alert('File too large', 'Choose a photo, video or file under 50 MB.');`
2. lib/uploadBody.ts:6-12 — `readUploadBody(uri, maxBytes = 50 * 1024 * 1024)` throws 'Choose a file smaller than 50 MB.' twice, once on `file.size` and once on `body.byteLength`.
3. The bucket. supabase/app_feature_expansion.sql:314 — `('chat-attachments', 'chat-attachments', false, 52428800, array[...])`. 52428800 bytes is exactly 50 MiB, and supabase/migrations/20260918093000_chat_phone_attachment_formats.sql:1 restates the intent in its own header comment: "Preserve the private bucket and 50 MiB limit; accept common phone and document formats." supabase/release_hardening.sql:59-74 raises a bucket to 104857600 (100 MiB) but its `where id = 'app-assets'` means chat-attachments was NOT raised. So even with both client caps removed, storage returns 413.
Sizes: a one-minute iPhone 4K/60 clip is ~400 MB, 4K/30 ~350 MB, 1080p/30 ~130 MB. Even 1080p does not fit under 50 MB. Note components/ChatAttachments.tsx:43 already passes `videoQuality: UIImagePickerControllerQualityType.Medium`, but that option applies only to video RECORDED through the picker, not to an existing library item, and the camera branch at :37 does not pass it at all.
What is installed: package.json has expo-image-picker 57.0.19, expo-video, expo-file-system, expo-image. There is NO compression package of any kind — no expo-image-manipulator, no react-native-compressor, no ffmpeg wrapper (confirmed against node_modules).
**fix plan** Compress, do not just raise the cap. Concretely:
1. Add react-native-compressor (it has an iOS/Android video transcoder with a progress callback and works with Expo prebuild) and call it in components/ChatAttachments.tsx `pick()` (:26-51) on the video branch, targeting 720p/2 Mbps. A one-minute clip lands around 15-20 MB, inside the existing bucket limit — no SQL change needed, which is the lowest-risk option.
2. Raise the ceiling anyway so an already-compressed clip is not rejected at the edge: a new migration `update storage.buckets set file_size_limit = 209715200 where id = 'chat-attachments';` (200 MiB), and lift the two client constants (ChatAttachments.tsx:63 and the uploadBody.ts default) to match. The bucket must be raised in the SAME change or the client cap change does nothing.
3. Pair this with the streaming-upload fix in C3/NEW-3 — a 150 MB ArrayBuffer read (lib/uploadBody.ts:10) will OOM the app before the network is even reached.
4. Show real progress during the transcode and the upload; a 60 s video will take tens of seconds and the current bare spinner (ChatAttachments.tsx:131) will look frozen again.
If adding a dependency is not acceptable this cycle, the fallback is: cap recording at 30 s in the camera branch (ChatAttachments.tsx:37 `videoMaxDuration` is already 120, lower it) and tell the member plainly why, rather than failing after a long upload.
**risk** react-native-compressor is a native module: NEW EAS BUILD, not an OTA update (DO-NOT-BREAK #22). Raising file_size_limit must not make the bucket public or change allowed_mime_types (DO-NOT-BREAK #20: chat-attachments stays private, read through signed links). Transcoded output must stay a MIME type the bucket allows — 'video/mp4' is in the list (app_feature_expansion.sql:314); do not emit anything else. Bigger objects also mean longer signed-URL fetches; the 120 s storage timeout in lib/supabase.ts:15 applies to uploads with a body but check downloads too.

**files** lib/chatService.ts:173, lib/chatService.ts:374, supabase/rls_policies.sql:91, supabase/rls_policies.sql:105, app/chat-room.tsx:155
